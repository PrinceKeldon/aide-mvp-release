# AIDE Publishing Calendar

Last updated: April 6, 2026

## Purpose

This document turns the AIDE build-in-public material into a concrete publishing schedule.

The goal is to make publication operational, not aspirational.

It should help answer:

- what gets published first
- when it gets published
- what supporting assets are needed
- what short-form posts support each long-form piece
- what needs to be done before pressing publish

Once this calendar is in motion, the publication side can run with low ambiguity while product development continues.

## Publishing Rules

1. One clear idea per week

- each week should have one primary long-form theme
- X supports the theme, not the other way around

2. Lead with the plain-language product story

- do not open the series with protocol detail
- start with the human problem and visible product shape

3. Pair every long-form post with short-form reinforcement

- one article
- one launch thread
- two to four supporting X posts

4. Use screenshots and product artifacts when possible

- `/mesh`
- `/your-day`
- `/m-peer`
- model diagnostics if useful

5. End each piece by pointing to the next one

- keep the reading path continuous

- three X posts per week

- one long-form article every 14 days
- two X posts per week

## Publication Checklist

Use this checklist before each weekly publish.

### Long-form article

- title chosen
- alternate title saved
- opening hook still sharp
- subheads scan cleanly
- closing CTA points to next piece
- final public link inserted where needed

### X launch thread

- launch thread drafted
- companion posts selected
- screenshots chosen if needed
- first reply prepared

### Links

- series index updated if needed
- pinned thread updated if needed
- GitHub or public landing link inserted

### Assets

- screenshots exported
- filenames stable
- alt text or caption notes prepared

## Publication Ownership

Suggested lightweight workflow:

1. finalize article
2. publish article
3. publish launch thread same day
4. publish one support post 2 days later
5. publish one support post 4 to 5 days later
6. prepare next article while the current one circulates

## Decision Point After Week 6

At the end of the first 6-week cycle, review:

- which posts got the strongest response
- which concepts people understood fastest
- which ideas caused confusion
- whether future posts should lean more product, more architecture, or more demos

That review should shape the next cycle.

## After Publication Closes

Once this initial publication cycle is scheduled and the assets are ready, the content system is strong enough to run in the background while product work continues.

That is the handoff point back into active build mode.
